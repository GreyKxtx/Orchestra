# Режим orchestra против обычных подагентов

Документ отвечает на один вопрос: чем режим `orchestra` отличается от «родитель
спавнит подагентов», который есть в любом современном агентном инструменте.
Ответ собран по коду, а не по спеке: спека описывает целевое состояние,
здесь — то, что выполняется сегодня.

Спецификация механики — [orchestra-routing.md](orchestra-routing.md),
конвейер воркеров — [planner-worker.md](planner-worker.md), состав режимов —
[../modes.md](../modes.md).

## Краткий ответ

Противопоставление «оркестра против подагентов» некорректно на уровне кода.
Подагентов запускает одна машина — `TaskRunner` в `internal/tasks`, — и ядро
собирает её одинаково для любого родительского режима
(`core.buildChildAgentConfig`). Ни одна ветка в `TaskRunner` не спрашивает, в
каком режиме работает родитель.

То, что называют «оркестрой», состоит из трёх независимых слоёв, и только
средний из них — собственно режим:

| Слой | Чем включается | Что даёт |
| --- | --- | --- |
| 1. Роль ребёнка | `subagent_type` в вызове `task` | Контракт задания, скоуп записи, верификация, тиры |
| 2. Ограничения Lead | родительский режим `orchestra` | Родитель не может писать код |
| 3. Машина состояний | наличие `.orchestra/state.md` | Фазы, контракт, гейты спавна и переходов |

Слои включаются порознь. Из режима `build` можно спавнить верифицируемых
воркеров; в режиме `orchestra` без файла состояния фазовые гейты молчат.

## Слой 1. Роль ребёнка

Обычный подагент (`explore`, `general`, `debug`) — это агент в другом режиме:
свой системный промпт, свой набор инструментов, свой лимит шагов, без истории
родителя. Ровно то, что дают подагенты в других инструментах.

`worker` — другое существо. Всё перечисленное ниже включается по
`subagent_type == "worker"` (`tasks.Spawn`, `tasks.runChild`), а не по режиму
родителя.

| | `general` / `debug` | `worker` |
| --- | --- | --- |
| Вход | свободный текст | WorkOrder JSON; проза заворачивается в WorkOrder с дефолтными критериями приёмки |
| Границы записи | нет | только `target_file(s)` из WorkOrder (`WorkerEditPaths`) |
| Бюджет промпта | общий | 48 КБ, без памяти проекта и session notes |
| Выход | произвольный | `task_result` со строгой схемой; `blocked_reason` из закрытой таксономии |
| После ответа | ничего | LSP-диагностика → `go build` → затронутые тесты → typecheck фронта → `acceptance_checks` → опционально LLM-верификатор → повтор с подсказкой → эскалация тира |
| Модель | родительская | из `orchestra.tiers[tier]` |
| Знания | конвенции + `decisions.md` | уроки и плейбук отдела |

Параллельность и её безопасность тоже живут здесь, не в режиме:

- Лимита на число одновременных детей нет: непересекающиеся воркеры стартуют
  разом.
- Пересечение скоупов записи проверяется под одним локом при регистрации
  задачи (`tasks.Spawn`, `conflictingTasksLocked`); пересекающиеся воркеры
  сериализуются, граф ожидания ацикличен по построению.

Практическое следствие: `task{subagent_type: "worker", …}` из режима `build`
даёт весь конвейер целиком. Для верифицируемых воркеров режим `orchestra` не
нужен.

## Слой 2. Режим orchestra — ограничения на Lead

Режим не добавляет детям ничего. Он отнимает у родителя право делать работу
самому и даёт ему бухгалтерию.

- **16 инструментов** (`orchestraLeadToolNames`): чтение, поиск, `repo_map`,
  делегирование, `question`, память на чтение, `write`,
  `update_working_state`, `contract_freeze`, `lesson_promote`,
  `playbook_promote`. Нет `edit`, `bash`, LSP, `todowrite`. Скиллы Lead не
  предлагаются намеренно (`agent_prompt.go`).
- **Запись только в** `.orchestra/plans|state.md|depts`
  (`plan.IsOrchestraLeadWritablePath`), а `final.patches` в production-файлы
  отвергаются с указанием делегировать (`run_final.go`).
- **Explore-first**: писать даже в план нельзя, пока репозиторий не прочитан.
- **Диета контекста**: результаты воркеров сжимаются до сводки и складываются
  в scratchpad отдела; каталог инструментов в промпт не идёт.
- **Своя модель**: `orchestra.planner` вместо `llm:`.

Это и есть то, чего режим `build` не гарантирует: там ничто не мешает
родителю после неудачного воркера дописать код самому.

## Слой 3. Машина состояний сессии

Фазы `discovery → documentation → contract → execution → delivery`, плюс
`maintenance`. Включается **существованием файла** `.orchestra/state.md`, а не
режимом: нет файла — гейты молчат в любом режиме; есть файл — они срабатывают
и на воркера, спавненного из `build`. Это сделано намеренно, иначе
`build`-родитель обходил бы контракт.

Два гейта:

- **`GuardSpawn`** — фазовый гейт перед спавном. Закрытый список исключений:
  спавнить в любой фазе можно только детей, которые либо не пишут вовсе
  (`explore`, `ask`, `verifier`), либо пишут строго в артефакты своей фазы
  (`architecture`, `product`, `documentation`). Всё остальное, включая
  неизвестный тип, считается пишущим и гейтится.
- **`GuardPhaseTransition`** — условия входа в фазу при записи `state.md`.
  Проверяется только то, что рантайм видит на диске: одобренный PRD,
  наличие L1 conventions, замороженный контракт, пустой `doc_debt`. Каждый
  отказ несёт путь разблокировки, у каждого условия есть вейвер.

Отсюда важное различие: «режим оркестры» как переключатель и
«оркестрированная сессия» как состояние проекта — разные вещи и включаются
порознь.

## Обоснованность

Два признака того, что это спека по слоям, а не надстройка ради надстройки.
Первый — единый движок: нет параллельных реализаций спавна, верификации или
скоупа. Второй — слои отвечают инвариантам спеки: «Zero Context Rot» — слой 1,
«Lead не пишет код» — слой 2, «Contract-first / fail-closed spawn» — слой 3.

Цена честная: 16 ручек в `orchestra:`, файл состояния, фазы. Первый реальный
прогон ветки дал 148 вызовов модели на две правки при нуле изменений на диске
(зафиксировано в [../coverage-map.md](../coverage-map.md)); причина найдена и
закрыта, но зелёного прогона в наборе у ветки пока нет.

## Что не проверяется

Честный список границ, чтобы их не приписывали механизму:

- **Интеграция после fan-out.** Каждый воркер верифицируется отдельно.
  Того, что 20 зелёных воркеров собираются вместе, не проверяет никто:
  у Lead нет сборки, а `verifier` над всем изменением — указание промпта, не
  гейт. Условия «эпики закрыты» и «verify зелёный» из таблицы переходов спеки
  не имеют реестра, по которому их можно прочитать, поэтому гейт delivery
  проверяет только `doc_debt`. Сделать его детерминированным мешает оверлей:
  в dry-run правки до диска не доходят, и сборка с тестами пропускается
  (`VerifyWorkerOutcome`), а обычный прогон идёт именно в dry-run.
- **Качество нарезки.** Ошибка Lead в контракте умножается на число воркеров;
  рычаг работает в обе стороны.
- **Выигрыш по деньгам и времени.** Не измерен. Параллельность даёт выигрыш
  по календарю только на провайдере, который тянет столько же одновременных
  запросов; на одной локальной видеокарте запросы встают в очередь. Суммарное
  число токенов при делегировании растёт, а не падает: экономия — в том, что
  они идут на дешёвый тир.

## Что это меняет в позиционировании

Три утверждения, каждое проверяемо по коду и каждого нет в подагентах из
коробки:

1. Lead физически не может тронуть код.
2. Каждый воркер проверяется сборкой и тестами до принятия, с эскалацией
   модели при провале.
3. Код не меняется до замороженного контракта.

Само по себе «родитель делит задачу на детей» новизной не является.
