# Модель безопасности: что Orchestra делает на машине пользователя

Orchestra читает чужой код, передаёт его модели и исполняет то, что модель предлагает. Поэтому у ядра три границы:
- что может репозиторий;
- что может модель;
- что уходит наружу.

Этот документ описывает, как устроена каждая. Находки, из-за которых границы появились, собраны в [аудите 2026-09](architecture-audit-2026-09.md) под ID SEC-*, ORC-*, LLM-*.

## 1. Что может репозиторий: доверие к рабочей области

`.orchestra.yml` коммитится и приезжает с каждым клоном. Часть его настроек действует на машину сама по себе. Эти настройки применяются **только в доверенной рабочей области**:

| Настройка | Почему опасна |
|---|---|
| `mcp.servers`, `.mcp.json` | запускают процессы при старте ядра |
| `hooks` | команды на событиях сессии и инструментов |
| `lsp.servers` | команды языковых серверов |
| `exec.confirm: false`, `exec.allow`, `exec.env_passthrough` | модель запускает команды без вопроса или получает секреты |
| `web.confirm: false` | сеть без вопроса |
| `permissions.rules` с `action: allow` | снимают согласие с инструмента |
| `llm.auth`, `providers.*.auth` | `token_command` запускает процесс |
| endpoint, куда ушёл бы ключ пользователя | `api_key: ${VAR}` или `${VAR}` в `api_base`, либо `api_base` проекта при ключе из `~/.orchestra/config.yml` |

Обычный конфиг — свой `api_base` без ключа (LM Studio, vLLM), модель, лимиты — не содержит ничего из этого и доверия не требует.

**Как работает.**
1. Load собирает «опасный срез» из `.orchestra.yml`, `.orchestra.local.yml` рядом с ним и `.mcp.json` и сверяет его отпечаток с `~/.orchestra/trusted-workspaces.json`.
2. Если отпечаток не записан, срез не применяется.
3. Ключ для чужого endpoint заменяется литералом, который проект записал сам, или пустым значением.
4. Ядро и CLI пишут в stderr, что проигнорировано; `workspace.trust_status` отдаёт то же клиенту.
5. Любое изменение среза (pull, правка агента) снова требует доверия. Поэтому запись агента в `.orchestra.yml` не превращается в исполнение кода в следующей сессии.

**Как доверить.**
- `orchestra trust` в каталоге проекта (`--status` покажет, что игнорируется; `--revoke` забудет рабочую область);
- RPC `workspace.trust` — перезапускает MCP без перезапуска ядра;
- `orchestra init` доверяет конфигу, который создал сам;
- `Save` через Orchestra в уже доверенной рабочей области сохраняет доверие. В недоверенной сохраняет файл, но не доверяет ему: сохранение другой настройки не должно ручаться за то, что принёс проект. Проигнорированные ключи при этом остаются в файле нетронутыми.

**Выключить проверку** может только пользователь: `security: { workspace_trust: off }` в `~/.orchestra/config.yml` или `ORCHESTRA_WORKSPACE_TRUST=off` в окружении (контейнеры, CI). Проект выключить её для себя не может.

## 2. Что может модель

- **Инструменты режима — граница.** Диспетчер отклоняет зарегистрированный инструмент, которого режим не предложил. Имя, которое вообще не является инструментом, получает прежний ответ «unknown tool».
- **`final.patches` проходят те же правила**, что `write` на тот же путь. Режим без `write` (explore, scout, ask, verifier) патчей не возвращает. Plan, orchestra и architecture держат свои области записи. Worker пишет только в `target_files` своего WorkOrder, product и documentation — в свои каталоги.
- **Режимы только для чтения делегируют только читателям.** Plan, architecture и ask на верхнем уровне порождают только explore, ask, scout и verifier, в том числе после маршрутизации `task_type`. Кастомный агент на читающей базе, которому дали `write`, считается пишущим и для phase guard.
- **Exec.**
  - `bash` требует согласия: `--allow-exec`, `exec.confirm: false` в доверенной рабочей области, allow-правило или вопрос пользователю.
  - `exec.allow` проверяет **каждую** команду, которую запускает shell-строка (`internal/execpolicy`). Отклоняются подстановки `$(…)` и `` `…` ``, подоболочки, here-документы, нелитеральное имя команды, присваивания `PATH`, `LD_*`, `GIT_SSH*` и запись вывода в файл.
  - Путь (`./go`, `tools/go`, `/usr/local/bin/go`) не считается программой из allowlist.
  - Запрос на одобрение показывает команду целиком: до 16 KiB, дальше явно сказано, сколько не показано.
- **Окружение команд.** `bash` (обычный и фоновый) запускается без переменных, похожих на секреты: `…_API_KEY`, `…SECRET…`, `…_PASSWORD`, `ORCH_API_KEY`, `ORCH_MCP_TOKEN` и т.п. Нужные проекту переменные перечисляются в `exec.env_passthrough`.
- **Пути.** Все инструменты разрешают пути внутри `project_root` с учётом symlink'ов и никогда не читают `.orchestra.env` и `.orchestra.local.yml`; `memory_read` читает только `.orchestra/memory/**`. `session_id` — простое имя (буквы, цифры, `.`, `_`, `-`).
- **Состояние оркестра.**
  - Поля, которыми владеет рантайм (`doc_debt`, `contract_epoch`, `clarification_rounds`, `blocked_since`, `prd_status`), модель через `update_working_state` не меняет.
  - Из waivers модель может объявить сама только `prd` и `contract` (для задачи, которую сочла маленькой); остальные выдаёт пользователь.
  - Агент верхнего уровня не завершает ход, пока его задачи работают.

## 3. Что уходит наружу

- **Сообщения агентов** приходят модели как информация от другого агента, а не как слова пользователя. Их угловые скобки экранируются: заметка не может закрыть блок `<agent_messages>`.
- **`webfetch`** ходит только по http(s). DNS разрешается один раз, и соединение идёт на проверенный IP. Loopback, частные, link-local, CGNAT и multicast адреса заблокированы, в том числе после редиректа.
- **Сетевые поверхности ядра** (`orchestra web`, `core --http`, `mcp serve --http`, `ckg-ui`) слушают loopback, если не сказано иное, и требуют токен. `ckg-ui` отдаёт исходники через ту же проверку путей, что и инструменты.
- **Секреты в логах** (`llm_log.jsonl`) редактируются; `authstore` пишет атомарно с правами 0600.
- **Провенанс памяти.** Память подмешивается в каждый следующий промпт, поэтому `memory_write` пишет в заголовок записи, кто её оставил: `*<время>* (by task_3_41, run <turn_id>) [project]`. Заметку, которую подагент записал по недоверенному содержимому, можно проследить до хода и агента.
- **Зависимости.** CI запускает `govulncheck`; бинарник собирается toolchain'ом из `go.mod` (`toolchain go1.25.14`).
