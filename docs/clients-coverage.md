# Что у клиентов работает, что проверено и что видно глазом

Карта по четырём поверхностям: консоль (`orchestra …` + TUI), веб, десктоп,
расширение VS Code. Отвечает на три разных вопроса, которые легко перепутать:

1. **Логика есть?** — код написан и делает то, что обещает.
2. **Проверено?** — и чем именно: тестом, руками или ничем.
3. **Видно?** — доходит ли это до пикселя, который видит пользователь.

Рядом: `coverage-map.md` — что проверено реальной моделью по режимам и
инструментам; `tools-status.md` — что вообще реализовано. Здесь — про клиентов.

Дата среза: 18.09.2026, `master`. Каждое утверждение ниже проверено по коду;
где сказано «не проверено» — значит не проверено, а не «наверное работает».

---

## Уровни доказательства

| Уровень | Что доказывает | Чего не доказывает |
|---|---|---|
| **Автотест** | логика на своём уровне | что это видно на экране |
| **Проверка сборки** (`check-web.mjs`, `check-webview.mjs`) | собранный бандл соответствует исходникам и разбирается | что он что-то рисует |
| **Руками** | что видно глазом | что не сломается завтра |
| **Ничего** | — | — |

Главный перекос проекта: **автотестов много, а тестов на то, что нарисовано, нет
почти нигде.** 2866 Go-тестов в 84 пакетах, 94 теста веб-адаптера, 47 тестов
расширения, 18 тестов десктопной оболочки — и ни одного, который смотрит на
готовый DOM или на кадр терминала целиком. Тесты веб-адаптера проверяют
**сообщения** между хостом и рендерером, а не результат отрисовки.

## 2. Консоль

`orchestra apply / core / web / eval / search / skills / mcp / llm-ping`.

- **Логика:** есть. `internal/cli` — 141 тест.
- **Проверено:** автотестами; три режима `apply` (direct / via-core /
  from-plan) закрыты интеграционными тестами со скриптованной моделью.
- **Видно:** да, это текстовый вывод.
- **Дыра:** интерфейс двуязычный — около 650 русских строк вперемешку с
  английскими, включая `orchestra --help`. Это единственная поверхность, где
  пользователь видит смесь сразу на первом экране.

### TUI

- **Логика:** есть, и она самая полная из всех клиентов. 297 тестов.
- **Видно:** диффы (`app_diff.go`), пофайловый разбор (`app_diff_review.go`),
  блоки инструментов, вывод `bash` по мере поступления.
- TUI — **единственный клиент, который обрабатывает `step_done`**, и до
  прошлой правки был единственным, кто умел применять правки выборочно.

## 3. Расширение VS Code

- **Логика:** есть. 47 тестов (`npm test`), плюс `check-webview.mjs` в CI и в
  публикации VSIX.
- **Видно:** чат со стримингом, блоки инструментов с иконками, именами,
  длительностью и предпросмотром аргументов (`05d-tools.js`), встроенные диффы,
  полоса ожидающих правок с разбором по файлам, подагенты, этапы workflow,
  расход контекста, модалки разрешений и вопросов.
- **Не проверено ничем:** сама отрисовка. Тесты расширения — это транспорт,
  разбор кадров и пути к бинарнику; ни один не открывает webview.
- **Дефект:** при падении процесса ядра расширение обнуляет `sessionId`
  (`coreSession.ts:1646`), и следующий ход молча начинает **новую** сессию.
  Сессия на диске остаётся, но пользователю об этом никто не говорит.

---

## 4. Веб

- **Логика:** есть. 94 теста адаптера гоняют **настоящий** `web.bundle.js` в
  песочнице `vm`, плюс `check-web.mjs`.
- **Видно:** ровно то же, что в VS Code — рендерер общий, фрагменты читаются из
  `ui/vscode/media/chat-src/` на месте, без копирования.
- **Дефект (обрывы — то самое):** разрыв сокета не переподключается. Клиент
  пишет «disconnected — reload to start a new session» (`40-projects.js:150`) и
  на этом всё. Между тем сессия на диске жива, и `session.start(session_id)`
  её восстановит — то есть переподключение возможно, просто не написано.
  Это следующее по очереди.

---

## 5. Десктоп

- **Логика:** оболочка рабочая — запускает ядро, ждёт объявления, открывает окно,
  гасит ядро при закрытии. 18 тестов на Rust (`boot.rs`, `sidecar.rs`), в CI
  идут `fmt`, `clippy -D warnings`, `test`, `build`.
- **Своего интерфейса нет:** в окне тот же `ui/web`, поэтому все веб-пункты
  выше относятся и к десктопу — включая обрывы.
- **Не доделано и помечено как не доделанное:** `bundle.active: false`,
  инсталляторов нет, подписи и автообновления нет.

## 6. Что из событий ядра доходит до экрана

Это ответ на вопрос «а визуализируются ли вызовы инструментов и правки».
Ядро испускает 14 видов событий потока плюс жизненный цикл подагентов.

| Событие | VS Code | Веб | TUI |
|---|---|---|---|
| `message_delta` (текст ответа) | да | да | да |
| `reasoning_delta` (рассуждения) | да | да | да |
| `tool_call_start` / `_delta` / `_completed` | да | да | да |
| `exec_output` (вывод bash по мере) | да | да | да |
| `pending_ops` (правки и диффы) | да | да | да |
| `step_usage` (расход токенов) | да | да | да |
| `context_estimate` (оценка контекста) | да | да | да |
| `todos_updated` (план работ) | да | да | да |
| `recoverable_error` | да | да | да |
| `child_started` / `child_done` (подагенты) | да | да | да |
| `workflow/stage_*` | да | да | — |
| `step_done` | нет | нет | да |

**Вывод: вызовы инструментов и правки в коде визуализируются во всех трёх
клиентах.** Блок инструмента показывает иконку, имя, путь, длительность и
статистику `+/−`; для `write` и `edit` он превращается во встроенный дифф.

Две клетки этой таблицы стали «да» этим же разбором — см. 7.1 и 7.3.

## 7. Найденные дефекты, по убыванию важности

### 7.1. В режиме автоприменения точный дифф выбрасывался · **починено**

Ядро считает настоящий дифф (было/стало по каждому файлу) и присылает его
событием `pending_ops`. Но:

- при `apply: false` приходит `applied: false` — оба хоста передавали его
  рендереру, и дифф встроенный, точный, с контекстом;
- при `apply: true` приходит `applied: true` с **теми же точными диффами** —
  и оба хоста выбрасывали полезную нагрузку, посылая только «панель убрать».

Что видел пользователь в режиме автоприменения: дифф, восстановленный блоком
инструмента из **аргументов вызова** (`04-diff-tools.js`, `extractDiffFromTool`).
Для `write` это `before = ""` — перезапись существующего файла рисовалась как
файл, целиком состоящий из новых строк. Для `edit` — только строки поиска и
замены, без окружающего кода и без номеров строк. То есть чем увереннее режим
работы, тем хуже было видно, что именно изменилось.

Исправлено: хосты шлют такие диффы отдельным сообщением `appliedOps`, которое
не поднимает панель подтверждения (подтверждать нечего — уже на диске), но даёт
блокам инструментов настоящий дифф.

### 7.2. Обрыв связи заканчивает разговор

Веб и десктоп: разрыв сокета не переподключается, предлагается перезагрузить
страницу и начать новую сессию. VS Code: падение ядра молча начинает новую
сессию. В обоих случаях сессия на диске цела — то есть это вопрос кода
восстановления, а не потерянных данных.

### 7.3. Этапы workflow не доходили до веба · **починено**

Рендерер рисовал полосу этапов с самого начала, но кормил её только хост
расширения. В браузере workflow шёл, а на экране про этапы не было ничего.

### 7.4. Смесь языков в интерфейсе

Около 650 русских строк вперемешку с английскими в TUI и CLI, включая
`orchestra --help`.

### 7.5. Десктоп не собирает установщик

Помечено как незаконченное самим проектом.

---

## 8. Чего нет вообще

- **Тестов на отрисовку.** Ни DOM-снимков, ни снимков кадра TUI. Любая
  регрессия внешнего вида ловится только глазами.
- **Прогонов с живой моделью после правок.** Последняя попытка отвалилась по
  таймауту из-за загруженного сервера.
- **Замера, ради которого всё затевалось:** проектный документ, разбитый на N
  страниц, оркестра против одного агента в режиме `build`, в долях принятых
  задач, долларах и минутах на принятую задачу.
