# Что у клиентов работает, что проверено и что видно глазом

Карта по четырём поверхностям: консоль (`orchestra …` + TUI), веб, десктоп,
расширение VS Code. Отвечает на три разных вопроса, которые легко перепутать:

1. **Логика есть?** — код написан и делает то, что обещает.
2. **Проверено?** — и чем именно: тестом, руками или ничем.
3. **Видно?** — доходит ли это до пикселя, который видит пользователь.

Рядом: `coverage-map.md` — что проверено реальной моделью по режимам и
инструментам; `tools-status.md` — что вообще реализовано. Здесь — про клиентов.

Дата среза: 18.09.2026, `master`. Каждое утверждение ниже проверено по коду;
где сказано «не проверено» — значит не проверено, а не «наверное работает».

---

## Уровни доказательства

| Уровень | Что доказывает | Чего не доказывает |
|---|---|---|
| **Автотест** | логика на своём уровне | что это видно на экране |
| **Проверка сборки** (`check-web.mjs`, `check-webview.mjs`) | собранный бандл соответствует исходникам и разбирается | что он что-то рисует |
| **Руками** | что видно глазом | что не сломается завтра |
| **Ничего** | — | — |

Главный перекос проекта: **автотестов много, а тестов на то, что нарисовано, нет
почти нигде.** 2866 Go-тестов в 84 пакетах, 94 теста веб-адаптера, 47 тестов
расширения, 18 тестов десктопной оболочки — и ни одного, который смотрит на
готовый DOM или на кадр терминала целиком. Тесты веб-адаптера проверяют
**сообщения** между хостом и рендерером, а не результат отрисовки.

## 2. Консоль

`orchestra apply / core / web / eval / search / skills / mcp / llm-ping`.

- **Логика:** есть. `internal/cli` — 141 тест.
- **Проверено:** автотестами; три режима `apply` (direct / via-core /
  from-plan) закрыты интеграционными тестами со скриптованной моделью.
- **Видно:** да, это текстовый вывод.
- **Дыра:** интерфейс двуязычный — около 650 русских строк вперемешку с
  английскими, включая `orchestra --help`. Это единственная поверхность, где
  пользователь видит смесь сразу на первом экране.

### TUI

- **Логика:** есть, и она самая полная из всех клиентов. 297 тестов.
- **Видно:** диффы (`app_diff.go`), пофайловый разбор (`app_diff_review.go`),
  блоки инструментов, вывод `bash` по мере поступления.
- TUI — **единственный клиент, который обрабатывает `step_done`**, и до
  прошлой правки был единственным, кто умел применять правки выборочно.

## 3. Расширение VS Code

- **Логика:** есть. 47 тестов (`npm test`), плюс `check-webview.mjs` в CI и в
  публикации VSIX.
- **Видно:** чат со стримингом, блоки инструментов с иконками, именами,
  длительностью и предпросмотром аргументов (`05d-tools.js`), встроенные диффы,
  полоса ожидающих правок с разбором по файлам, подагенты, этапы workflow,
  расход контекста, модалки разрешений и вопросов.
- **Не проверено ничем:** сама отрисовка. Тесты расширения — это транспорт,
  разбор кадров и пути к бинарнику; ни один не открывает webview.
- **Восстановление после падения ядра:** работает. Последний `session_id`
  лежит в `workspaceState`, и следующее обращение переоткрывает ту же сессию;
  composer освобождается из «Stop» блоком `finally`. Теряется только ход,
  который шёл в момент падения.

---

## 4. Веб

- **Логика:** есть. 94 теста адаптера гоняют **настоящий** `web.bundle.js` в
  песочнице `vm`, плюс `check-web.mjs`.
- **Видно:** ровно то же, что в VS Code — рендерер общий, фрагменты читаются из
  `ui/vscode/media/chat-src/` на месте, без копирования.
- **Обрывы (починено):** разрыв сокета переподключается сам и возвращает ту же
  сессию — см. 7.2.

---

## 5. Десктоп

- **Логика:** оболочка рабочая — запускает ядро, ждёт объявления, открывает окно,
  гасит ядро при закрытии. 18 тестов на Rust (`boot.rs`, `sidecar.rs`), в CI
  идут `fmt`, `clippy -D warnings`, `test`, `build`.
- **Своего интерфейса нет:** в окне тот же `ui/web`, поэтому все веб-пункты
  выше относятся и к десктопу — включая обрывы.
- **Не доделано и помечено как не доделанное:** `bundle.active: false`,
  инсталляторов нет, подписи и автообновления нет.

## 6. Что из событий ядра доходит до экрана

Это ответ на вопрос «а визуализируются ли вызовы инструментов и правки».
Ядро испускает 14 видов событий потока плюс жизненный цикл подагентов.

| Событие | VS Code | Веб | TUI |
|---|---|---|---|
| `message_delta` (текст ответа) | да | да | да |
| `reasoning_delta` (рассуждения) | да | да | да |
| `tool_call_start` / `_delta` / `_completed` | да | да | да |
| `exec_output` (вывод bash по мере) | да | да | да |
| `pending_ops` (правки и диффы) | да | да | да |
| `step_usage` (расход токенов) | да | да | да |
| `context_estimate` (оценка контекста) | да | да | да |
| `todos_updated` (план работ) | да | да | да |
| `recoverable_error` | да | да | да |
| `child_started` / `child_done` (подагенты) | да | да | да |
| `workflow/stage_*` | да | да | — |
| `step_done` | нет | нет | да |

**Вывод: вызовы инструментов и правки в коде визуализируются во всех трёх
клиентах.** Блок инструмента показывает иконку, имя, путь, длительность и
статистику `+/−`; для `write` и `edit` он превращается во встроенный дифф.

Две клетки этой таблицы стали «да» этим же разбором — см. 7.1 и 7.3.

## 7. Найденные дефекты, по убыванию важности

### 7.1. В режиме автоприменения точный дифф выбрасывался · **починено**

Ядро считает настоящий дифф (было/стало по каждому файлу) и присылает его
событием `pending_ops`. Но:

- при `apply: false` приходит `applied: false` — оба хоста передавали его
  рендереру, и дифф встроенный, точный, с контекстом;
- при `apply: true` приходит `applied: true` с **теми же точными диффами** —
  и оба хоста выбрасывали полезную нагрузку, посылая только «панель убрать».

Что видел пользователь в режиме автоприменения: дифф, восстановленный блоком
инструмента из **аргументов вызова** (`04-diff-tools.js`, `extractDiffFromTool`).
Для `write` это `before = ""` — перезапись существующего файла рисовалась как
файл, целиком состоящий из новых строк. Для `edit` — только строки поиска и
замены, без окружающего кода и без номеров строк. То есть чем увереннее режим
работы, тем хуже было видно, что именно изменилось.

Исправлено: хосты шлют такие диффы отдельным сообщением `appliedOps`, которое
не поднимает панель подтверждения (подтверждать нечего — уже на диске), но даёт
блокам инструментов настоящий дифф.

### 7.2. Обрыв связи заканчивал разговор · **починено в вебе и десктопе**

Веб и десктоп: разрыв сокета не переподключался, предлагалось перезагрузить
страницу и начать новую сессию. Между тем ядро — отдельный процесс, который
держит реестр проектов, а сессия лежит на диске: и то и другое переживает
сокет. Теперь страница переподключается сама (немедленно, затем 0.5 / 1 / 2 /
4 / 8 с) и заново открывает **ту же** сессию, перерисовывая её из ядра —
ход, который шёл в момент обрыва, всё равно умер вместе с сокетом, поэтому
источником правды берётся запись ядра, а не то, что осталось на экране.
Исчерпав попытки, клиент говорит прямо, что связь потеряна.

**Поправка к более раннему утверждению:** про VS Code здесь было написано, что
падение ядра молча начинает новую сессию. Это неверно. Расширение хранит
последний `session_id` в `workspaceState` (`coreSession.ts`,
`LAST_SESSION_KEY`) и при следующем обращении переоткрывает именно её, а
composer освобождается блоком `finally`, который всегда шлёт `turnComplete`.
Теряется только ход, шедший в момент падения, — и это неизбежно.

### 7.3. Этапы workflow не доходили до веба · **починено**

Рендерер рисовал полосу этапов с самого начала, но кормил её только хост
расширения. В браузере workflow шёл, а на экране про этапы не было ничего.

### 7.4. Смесь языков — но не там, где казалось · **починено**

**Поправка.** Раньше здесь значилось «650 русских строк вперемешку с
английскими в TUI и CLI». Это не дефект: `language-policy.md` прямо решает, что
строки для оператора (справка CLI, интерактивные вопросы) — русские, а всё, что
читает модель (системные промпты, описания инструментов, их вывод), —
английское, и это закреплено тестами (`TestToolDefinitions_AreEnglish`).
TUI и CLI живут ровно по этому правилу.

**И вторая поправка, к самому счёту.** Число «156 строк» было артефактом
измерения: `grep` с диапазоном `А-Я` в байтовом режиме считал кириллицей любой
не-ASCII символ, включая `…`, `×` и все глифы иконок. Точный счёт — **27
строк** в графических клиентах.

Дыра при этом была настоящая: **они смешивали языки внутри одного экрана** —
«Working…» рядом с «Доступ» и «Инструменты», кнопки Keep / Drop рядом с
русской подсказкой про Accept/Reject. Политика писалась до появления
графических клиентов и про них ничего не говорит.

Решено многоязычностью, а не выбором одного языка: два каталога
(`ui/vscode/media/i18n.js` — общий для чата и панели настроек на обоих хостах,
`ui/vscode/src/i18n.ts` — для хоста расширения), английский как запасной
вариант для недостающего ключа, выбор языка прямо в панели настроек (раздел
«Общие»), который пишется в `orchestra.language` в VS Code и в
`localStorage["orchestra.lang"]` в вебе, с автоопределением по языку редактора
или браузера. Добавление третьего языка — один объект в каждом каталоге.

**Доведено до конца вторым заходом.** Первый заход перевёл только строки,
которые собираются в JS, и часть разметки; сама разметка чата (в `panel.ts` и
`index.src.html`), панель настроек целиком, боковая панель проектов и
стартовый экран остались английскими. Теперь через каталог проходят все четыре
поверхности: 476 ключей, 372 из них — в разметке. Не переводится намеренно то,
что принадлежит не нам и лишь проходит насквозь: идентификаторы моделей и
имена провайдеров из удалённого каталога, описание навыка из его файла,
подписи ролей из ядра и текст ошибки, процитированный у ядра или провайдера.

Обе проверки (`check-webview.mjs`, `check-web.mjs`) сверяют каждый ключ
разметки с каталогом: опечатка в ключе — не ошибка нигде, `i18n()` вернёт сам
ключ, и на экране вместо «Готово» тихо появится `set.mcp.done`.

### 7.5. Панель настроек в вебе и десктопе вообще не открывалась · **починено**

Найдено не тестом, а отрисовкой: страница открывается в headless-браузере,
снимок читается обратно как картинка. Тесты были зелёными, проверки сборки
тоже, а по кнопке-шестерёнке открывался пустой диалог.

Причина — политика безопасности, которую я же и завинтил в прошлый заход.
Панель настроек — это **второй наш документ** в `<iframe>` (у неё свой
`:root` с теми же именами токенов, что у чата, поэтому встроить её в ту же
страницу нельзя). Под `default-src 'none'` кадр запрещён дважды: `frame-src`
не разрешал его загрузить, а `frame-ancestors 'none'` запрещал странице чата
быть его предком. Обе директивы добавлены (`'self'`), защита от кликджекинга
не ослаблена: чужой origin по-прежнему обрамить нас не может.

Отдельный урок про наблюдаемость: **заблокированный кадр — это строка в
консоли, а не ошибка, которую страница может поймать.** Ни один слой не мог
об этом сообщить. Тест теперь привязан к разметке: есть `<iframe>` — обе
директивы обязаны быть.

### 7.6. Иконки не были системой · **починено**

Найдено так же, как 7.5 — глазами, на запущенном десктопе.

Две жалобы оказались одной причиной. **Первая:** у выполненного шага не было
опознавательного знака — `updateToolHead` заменяла иконку инструмента на `✓`,
то есть у почти всего, что на экране, иконки не оставалось; а `git.log`,
`lsp.*`, `gh.*`, `mcp:*`, `webfetch` не попадали ни в один `toolKind` и
получали `•`. **Вторая:** контролы выглядели «не частью дизайна». Причина —
иконок как системы не существовало: **32 разных юникодных глифа в 96 местах**
(`∞ ◎ ◌ ▣ ≡ ⌕ ◇ ⌁ ◫ □ ▾ → ← ✱ ✦ ◈ $`), каждый рисуется тем шрифтом, который
его несёт, а `⌁` и `◫` на Windows вообще выпадают из шрифта интерфейса; рядом
— нарисованные руками SVG на 14/15/16/18/22 px, на двух сетках, четырьмя
толщинами обводки. Шеврон на пилюлях стоял на `font-size: 7px` и читался как
случайная точка. Высоты контролов в одном ряду: 22 / 26 / 28 / 32.

Что сделано: один набор `ui/vscode/media/icons.js` (сетка 24, обводка 1.75,
57 иконок, одна на четыре бандла — как `i18n.js`), одна шкала размеров
(`--icon-*`, `--ctl-h-*`, `--r-*`), тело результата инструмента с
форматированным JSON, разворотом целиком и копированием исходных байт.
Подробности и правила — `docs/ui-design-system.md`.

Сторожит это сверка в обеих проверках бандлов: имя иконки, которого нет в
наборе, рисует **пустоту** без единой ошибки где-либо, и это ловится; `<svg>`,
нарисованный руками в `panel.ts` или на отдаваемой странице, тоже. Обе проверки
проверены на падение.

### 7.7. Десктоп не собирает установщик

Помечено как незаконченное самим проектом.

## 8. Чего нет вообще

- **Тестов на отрисовку — почти.** Первый появился вместе с переключением
  языка: он проверяет, что после смены языка в DOM меню лежит другой текст, а
  не только что сообщение дошло. Остальное по-прежнему ловится глазами: ни
  снимков DOM, ни снимков кадра TUI. Статическую разметку этот тест не
  покрывает — песочница адаптера не разбирает HTML, поэтому её сторожит
  сверка ключей с каталогом, а не проверка нарисованного.

  **Чего это стоит, видно по 7.5:** панель настроек в вебе не открывалась
  вообще, и ни один из ~3000 тестов этого не заметил. Нашлось за минуту, как
  только страницу отрисовали в headless-браузере и посмотрели на снимок.
  Самый дешёвый следующий шаг в тестировании — не ещё один юнит-тест, а
  прогон «открыть страницу, снять кадр, прочитать консоль» в CI.
- **Прогонов с живой моделью после правок.** Последняя попытка отвалилась по
  таймауту из-за загруженного сервера.
- **Замера, ради которого всё затевалось:** проектный документ, разбитый на N
  страниц, оркестра против одного агента в режиме `build`, в долях принятых
  задач, долларах и минутах на принятую задачу.
