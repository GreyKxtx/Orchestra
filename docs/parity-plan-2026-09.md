### 1.3 Индекс и поиск по памяти — ● → ●● (закрыт)

**Есть.** `memory_search`: substring по всем слоям + семантическое ранжирование по **всей** памяти при `embed.model` (порог 0.15, `memory/semantic_index.go`, векторы в `ckg.db`); честный `degraded` при отказе embed (`fefffb2`).

| ~~1~~ | ~~Эмбеддинги **всей** памяти, а не последних 48 чанков~~ — закрыто | **Проверка перед работой изменила решение.** Рецепт «переиспользовать `node_embeddings` с типом узла `memory`» не выдержал сверки с кодом: `node_embeddings.node_id` — FK на `nodes(id)`, а `nodes` требует `file_id` → `files(id)` плюс `fqn/kind/line_start/line_end` (`ckg/store.go:110,177`), то есть под каждый чанк памяти пришлось бы заводить синтетические строки в двух таблицах; `nodes` читают `explore`/`symbols`/`repo_map`, и память всплывала бы там как символы кода, пока каждый потребитель не отфильтрует `kind != 'memory'` — один забытый фильтр даёт тихо неверный ответ; `MissingEmbeddings` жёстко ограничен `kind IN ('func','method','struct','interface','type')` (`embed_store.go:118`), а индексатор берёт текст через `ReadNodeSource` — читает файл по пути и диапазону строк (`embedindex.go:134`), которых у чанка памяти нет.
